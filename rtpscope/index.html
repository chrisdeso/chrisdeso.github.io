rtpscope

A video call we build end to end. It steps its own quality down when the network gets worse and explains every drop it couldn't avoid.

TL;DR

rtpscope is now a video call app we build ourselves: a browser client plus a small Python server. It lowers its own video quality (1080p → 720p → 480p) when the network gets worse. It also tells you why each quality drop happened: the sender's connection, the receiver's connection, a jittery network, or one of the computers. That's our CS 4372 project (Project #5). Progress report Oct 28, presentation Nov 23, code + final report Dec 5.

Terms used below
WebRTC
the browser's built-in way to do live audio/video calls. We use it for capture, encoding and sending.
RTP
the format that carries a call's actual audio and video, packet by packet.
Signaling server
the small server that introduces two browsers to each other. After that, the media goes directly between them.
Jitter
how uneven the timing between packets is, not how many get lost.
Jitter buffer
a short waiting line at the receiver that smooths out jitter. A bigger buffer means smoother playback but more delay.
Ladder / rung
our three quality levels (1080p, 720p, 480p), each with a bitrate. "Stepping down" means moving to a lower rung.
netem
a Linux tool that adds delay, jitter, packet loss or a bandwidth cap to a network link on purpose.
PSNR
a quality score for how close the received frame is to the original. We can compute it because we have the original.

Why this

The project asks for a two- or multi-user call that copes with a bad network and measures how well it copes. Our first idea was figuring out whose fault a bad call is, and that's now the measuring part of the call. Building both ends makes it easier, not harder. We can read stats from both sides on one timeline, and we have the original video to compare against, so we score quality directly instead of guessing.

The parts that are ours: the logic that picks the quality rung, our own jitter buffer and audio/video sync, and the measurement pipeline. WebRTC, ffmpeg and tc are the tools.

How it decides who's at fault

Five situations, each with a different fingerprint across the two ends. In testing we cause each one on purpose, so we always know the right answer:

What needs to be built

call+adaptation

Task: browser client, Python signaling server, and the code that picks the quality rung. First goal: two browsers in a call through our server. Stretch: a third person in the call.

buffering+sync

Task: a Python receiver with our own jitter buffer and audio/video sync, plus a test pattern (a timestamp barcode and a flash + beep each second). First goal: the Python receiver joins a call and plays it.

testbed+measurement

Task: the fake network we break on purpose, the stats logger, PSNR, the fault table, and the plots. First goal: two browsers on the fake network with both sides' stats in one CSV.

Call and testbed can start right away, fully in parallel. Buffering can start on the test pattern and the Python receiver right away too, but it needs a working call before it has real data to work with, so plan on that.

Questions I had working through this

Why build our own call instead of measuring Google Meet?

The project asks us to build it, and building it gives us things Meet never would. We get stats from both ends, the original video to score against, and the chance to write our own adaptation and buffering, which is the part we're supposed to build ourselves.

What happened to the packet sniffing and screen capture?

We don't need them anymore. Stats from both ends replace the sniffing, and comparing against the original video (PSNR) replaces guessing quality from screenshots. Reading packet headers could come back later as an optional cross-check.

Do we need root?

Only to set up the fake network (namespaces and tc rules). The call itself runs as a normal user.

Isn't Chrome already adapting quality on its own?

Yes, and that's one of the things we compare against. We test four strategies: fixed 1080p, Chrome's default, and two of our own. Then we report which one gives the best balance of quality and delay.

What do we actually turn in at the end?

Slides and a live demo, then code that runs and reproduces our results, plus the final report.
