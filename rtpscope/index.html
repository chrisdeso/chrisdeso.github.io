CS 4372 · Team Brief

rtpscope

the short version — read this before the full proposal
TL;DR

rtpscope watches a video call two different ways at once — the raw network packets, and the actual pixels rendered on screen — and cross-references them to figure out whose fault it is when a call looks bad: your connection, the other person's, your computer, or their encoder. That's our CS 4372 project. Proposal is due Sept 21, a working prototype by Oct 28, demo Nov 23–Dec 7.

Terms used below
RTP
the protocol that actually carries a call's live audio/video packets.
SRTP
RTP, encrypted — what Meet, Jitsi, and Discord actually use.
Jitter
how unevenly packets are arriving, not how many are lost.
No-reference metric
a quality score with no access to the original video — we never get the other person's raw camera feed to compare against.
Wire / Pixel path
our two data sources — the network capture, and the on-screen capture.

Why this

Every video call app tells you when a call is bad. None of them tell you why. Chrome's own call statistics only see what was handed to the video decoder — not what actually made it onto the screen — so they miss real problems, like your display freezing while the network is completely fine. Watching the network and the screen independently, at the same time, is how you tell those cases apart.

How it decides who's at fault

Four situations, each with a different fingerprint across the two signals:

Network saysScreen saysCulprit
loss high, bitrate collapsingblocky, freezingYour link
loss ~0, bitrate dropped on purposelower res, no freezeThe far end
loss ~0, bitrate steadyfrozen, decode stallsThis machine
loss ~0, bitrate steadyblocky, no freezeTheir encoder

Who's building what

Wire path

Task: packet capture + RTP header parser. First goal: print live bitrate/loss/jitter for one call to a terminal.

Pixel path

Task: screen capture + no-reference quality scoring. First goal: print a blockiness/freeze number for the same call.

Correlation + HUD

Task: merge both series, apply the fault table above, build the overlay. First goal: the fake-data mock-up above, for real.

Wire and pixel can be built fully in parallel — neither needs the other to exist first. Correlation genuinely can't start for real until both are producing real numbers, so plan on that person prototyping the HUD against fake data (like above) in the meantime, not sitting idle.

Get set up

  • [ ]A Linux machine (or VM) on GNOME or KDE Wayland — Sway/Hyprland have weaker screen-capture support, avoid for now.
  • [ ]Python 3 + libpcap. One-time: sudo setcap cap_net_raw+ep <binary> — no sudo needed to actually run it after that.
  • [ ]A WebRTC call to test against — Google Meet or Jitsi, not Zoom/Teams (see FAQ).
  • [ ]tc netem (ships with iproute2 on basically every distro) — we'll use it later to fake network problems on purpose.

Questions you probably have

Why not just test on Zoom or Teams?

They hide their packet framing beyond plain SRTP, so we can't read bitrate/loss/jitter off the wire the same way. Meet and Jitsi are both plain WebRTC — that's why we're scoping to those.

Do we need root to run this?

Only once, to grant the capture binary permission via setcap. After that it runs as a normal user, every time.

Is it okay to capture our own call's packets?

Yes — we only ever read headers (metadata) off our own machine's own network interface, for our own call. We never decrypt anyone's actual audio or video.

What if screen capture doesn't work on someone's laptop?

GNOME/KDE Wayland is the reliable path; keep an X11 session as a fallback if your setup is something else.

What do we actually turn in at the end?

Two things: a CSV + written report generator (the real deliverable) and the live overlay HUD (the demo surface) — both shown above.
