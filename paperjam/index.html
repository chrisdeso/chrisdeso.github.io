CS 4372 · Team Brief

paperjam

the short version — read this before the full proposal
TL;DR

paperjam turns a real e-ink display into a playable two-player Pong game by treating its refresh mode as a per-region scheduling problem instead of one fixed global setting — the scoreboard stays crisp while the ball updates fast enough to actually play. Alternative CS 4372 project idea (see the compare link above for rtpscope). Same dates: proposal Sept 21, prototype Oct 28, demo Nov 23–Dec 7.

Terms used below
Waveform
the drive sequence that moves an e-ink pixel from one shade to another — different waveforms trade speed for quality.
Ghosting
a faint trace of the previous image left behind after a fast refresh.
SSIM
Structural Similarity Index — the standard image-quality metric from the course's compression unit, 0–1, comparing a frame to a clean reference. We use it to score ghosting: 1.0 = identical, lower = more visible ghosting.
GC16 / A2 / etc.
preset waveform modes built into our display's controller chip (see table below).
IT8951
the chip that actually drives the panel and exposes those modes over SPI.
Partial refresh
updating just one region of the screen, independent of the rest.

Why this

E-ink is the display defined by what it can't do: motion. Every e-ink device ships with one fixed refresh policy for the whole panel — fine for reading, useless the moment a screen needs a crisp scoreboard and a fast-moving ball at the same time. Nobody has shipped something you can actually play, by feel, on e-ink. We think that's a software policy limit, not a hardware one, and we're going to prove it with a paddle.

How it picks a mode

Six built-in waveforms, each a different speed/quality tradeoff — assigned per region instead of to the whole screen:

Who's building what

Game + input

Task: game loop, ball physics, GPIO button wiring. First goal: one square moving in A2 mode from our own code.

Driver + hacking

Task: IT8951 SPI integration, partial-window addressing. First goal: one full-panel GC16 image, one A2 region update.

Scheduler + eval

Task: SSIM-threshold model, mode assignment, baselines. First goal: the demo above, driven by real data.

Game+input and driver work can start fully in parallel. Scheduler work needs both of those producing real frames before it can be evaluated for real — plan on that person prototyping the SSIM-threshold logic against the fake-data demo above in the meantime.

Questions you probably have

Why not just use a cheap $20 panel?

Those are 1-bit only (no IT8951, no GC16/DU4/A2 modes) — there'd be exactly one waveform to "adaptively" choose between, which deletes the whole point.

Do we need to write actual firmware?

No — the six built-in waveform modes are enough for the real project. Writing a custom waveform table is an optional stretch goal we've already flagged as likely infeasible on this specific chip (see full proposal).

What if partial-window updates don't work on our panel?

Fallback is choosing one waveform for the entire next frame instead of per-region — weaker, but still a real version of the same question, and it still beats a fixed baseline if the classifier is any good.

Is Pong actually going to feel playable at these refresh speeds?

That's an open, honest risk — even A2's ~120 ms is slower than a real Pong "wants" to feel. We decouple the physics tick from the panel's refresh rate to compensate; whether that's enough is part of what Milestone 2 tells us.

What do we actually turn in at the end?

A playable two-player Pong cabinet on real hardware, plus a measured comparison against two fixed-waveform baselines — both described above.
